# XML Design Guidelines

## Introduction

This document provides general guidelines for designing new XML document formats and, to some extent, XML documents (see Section 11). Document formats usually include formal parts, such as DTDs and schemas, and parts expressed in normative English prose.

These guidelines apply to new designs and are not intended to force retroactive changes in existing designs. When participating in the creation of public or private document format designs, the guidelines may be helpful but should not control group consensus.

This guide is intended for XML generated and consumed by machines rather than humans. Its rules are *not applicable* to formats such as XHTML, which should be formatted as much like HTML as possible, or ODF, which expresses rich text. A document that includes embedded XHTML or other rich-text content but also contains purely machine-interpretable portions SHOULD follow this style guide for the machine-interpretable portions. This guide also does not apply to XML document formats generated by translation from Protocol Buffers or another format.

Brief rationales accompany most guidelines. They are maintained in the same document in the hope that they remain current, but they are not normative.

The terms MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are used as defined by [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt "RFC 2119").

## 1. To design or not to design

1. Attempt to reuse existing XML formats whenever possible, especially formats that allow extensions. Create an entirely new format only with care and consideration; first read [Tim Bray's warnings](https://www.tbray.org/ongoing/When/200x/2006/01/08/No-New-XML-Languages "Tim Bray's warnings"). If possible, seek broad review of the format from outside your organization. *Rationale: New document formats have a cost: they must be reviewed, documented, and learned by users.*
2. When reusing or extending an existing format, make *sensible* use of its prescribed elements and attributes, especially required ones. Do not completely repurpose them, but consider creative uses when the standard semantics are unsuitable. As a last resort, when a required element or attribute is inappropriate for your use case, use a fixed string as its value. *Rationale: Markup reuse is good; markup abuse is bad.*
3. When extending formats, follow the existing format's implicit style, even when it contradicts this guide. *Rationale: Consistency.*

## 2. Schemas

1. Document formats SHOULD be expressed using a schema language. *Rationale: Clarity and machine-checkability.*
2. The schema language SHOULD be [RELAX NG](https://relaxng.org/ "RELAX NG") [compact syntax](https://relaxng.org/compact-tutorial-20030326.html "RELAX NG compact syntax"). Embedded [Schematron](https://schematron.com/ "Schematron") rules MAY be added for finer control. *Rationale: RELAX NG is a flexible schema language with few arbitrary design restrictions. Its compact syntax is easy to read and learn and can be converted one-to-one to and from the XML syntax when necessary. Schematron handles arbitrary cross-element and cross-attribute constraints.*
3. Schemas SHOULD use the [Salami Slice style](http://www.xfront.com/GlobalVersusLocal.html#SecondDesign "Salami Slice style") with one rule per element. Schemas MAY use the [Russian Doll style](http://www.xfront.com/GlobalVersusLocal.html#FirstDesign "Russian Doll style"), in which the schema resembles the document, when they are short and simple. The [Venetian Blind style](http://www.xfront.com/GlobalVersusLocal.html#ThirdDesign "Venetian Blind style"), with one rule per element type, is unsuited to RELAX NG and SHOULD NOT be used.
4. Regular expressions SHOULD be provided to assist in validating complex values.
5. DTDs and/or W3C XML Schemas MAY be provided for compatibility with existing products, tools, or users. *Rationale: We cannot change the world all at once.*

## 3. Namespaces

1. Element names MUST be in a namespace, except when extending pre-existing document types that do not use namespaces. A default namespace SHOULD be used. *Rationale: Namespace-free documents are obsolete; every set of names should be in a namespace. A default namespace improves readability.*
2. Attribute names SHOULD NOT be in a namespace unless they are drawn from a foreign document type or are intended for use in foreign document types. *Rationale: Attribute names in a namespace must always have a prefix, which is inconvenient to type and difficult to read.*
3. Namespace names are HTTP URIs. Namespace names SHOULD take the form `https://example.com/{format}/{year}`, where `format` is a unique value based on the document type's name and `year` is the year the namespace was created. Additional URI path segments may precede the year. *Rationale: This follows existing convention. Including the year allows code names to be recycled.*
4. Namespaces MUST NOT be changed unless the semantics of particular elements or attributes have changed in drastically incompatible ways. *Rationale: Changing the namespace requires changing all client code.*
5. Namespace prefixes SHOULD be short, but not so short that they are likely to conflict with another project. Single-letter prefixes MUST NOT be used. Prefixes SHOULD contain only lowercase ASCII letters. *Rationale: Ease of typing and the absence of encoding compatibility problems.*

## 4. Names and enumerated values

> **Note:** "Names" refers to the names of elements, attributes, and enumerated values.

1. All names MUST use lowerCamelCase. They start with an initial lowercase letter, and each new word begins with a capital letter. *Rationale: A single style provides consistency. It matches Java style, and other languages can use automated name conversion.*
2. Names MUST contain only ASCII letters and digits. *Rationale: Ease of typing and the absence of encoding compatibility problems.*
3. Names SHOULD NOT exceed 25 characters. Avoid longer names by devising concise and informative alternatives. If staying within this limit would make a name obscure, ignore the limit. *Rationale: Longer names are awkward to use and require additional bandwidth.*
4. Published standard abbreviations MAY be used when they are sufficiently well known. Ad hoc abbreviations MUST NOT be used. Acronyms MUST be treated as words for camel-casing purposes: `informationUri`, not `informationURI`. *Rationale: An abbreviation familiar to one community is often incomprehensible to others who use the same document format. Treating an acronym as a word also makes word boundaries easier to identify.*

## 5. Elements

1. All elements MUST contain either nothing, character content, or child elements. Mixed content MUST NOT be used. *Rationale: Many XML data models do not handle mixed content properly, and its use makes the element order-dependent. Textual formats are exempt from this rule.*
2. XML elements that merely wrap repeating child elements SHOULD NOT be used. *Rationale: They are not used in Atom and add nothing.*

## 6. Attributes

1. Document formats MUST NOT depend on the order of attributes in a start tag. *Rationale: Few XML parsers report the order, and it is not part of the XML Infoset.*
2. Elements SHOULD NOT be overloaded with too many attributes; use 10 as a rule of thumb. Instead, use child elements to encapsulate closely related attributes. *Rationale: This preserves XML's built-in extensibility and supports forward compatibility as a specification evolves.*
3. Attributes MUST NOT hold values in which line breaks are significant. *Rationale: Conforming XML parsers convert such line breaks to spaces.*
4. Document formats MUST allow either single or double quotation marks around attribute values. *Rationale: XML parsers do not report the difference.*

## 7. Values

1. Numeric values SHOULD be 32-bit signed integers, 64-bit signed integers, or 64-bit IEEE doubles, all expressed in base 10. These correspond to the XML Schema types `xsd:int`, `xsd:long`, and `xsd:double`, respectively. When required, `xsd:integer` values with unlimited precision MAY also be used. *Rationale: XML Schema has many numeric types; these provide a reasonable subset.*
2. Boolean values SHOULD NOT be used; use enumerations instead. If booleans are necessary, they MUST be expressed as `true` or `false`, corresponding to a subset of the XML Schema type `xsd:boolean`. The alternative `xsd:boolean` values `1` and `0` MUST NOT be used. *Rationale: Boolean arguments are not extensible. Parsers do not abstract away the additional flexibility of numeric values.*
3. Dates SHOULD be represented using [RFC 3339](https://www.ietf.org/rfc/rfc3339.txt "RFC 3339") format, a subset of both ISO 8601 and the XML Schema `xsd:dateTime` format. UTC times SHOULD be used rather than local times. *Rationale: Many date formats and time zones exist, although local time sometimes preserves important information.*
4. Embedded syntax in character content and attribute values SHOULD NOT be used. Syntax in values makes XML tools largely useless. Dates, URIs, and XPath expressions are exceptions. *Rationale: Users should be able to process XML documents using only an XML parser, without requiring additional special-purpose parsers that are easy to implement incorrectly.*
5. Be careful with whitespace in values. XML parsers do not strip whitespace in elements, but they convert newlines to spaces in attributes. Application frameworks may strip whitespace more aggressively. Document formats SHOULD define whitespace-stripping rules.

## 8. Key-value pairs

1. Simple key-value pairs SHOULD be represented by an empty element whose name represents the key and whose `value` attribute contains the value. Elements with a `value` attribute MAY also have a `unit` attribute for the unit of measurement. Physical measurements SHOULD use the [SI system](https://en.wikipedia.org/wiki/International_System_of_Units "International System of Units"). *Rationale: This provides simplicity and design consistency. Keeping the value in an attribute hides it from the user because displaying the value without its key is not useful.*
2. If the number of possible keys is very large or unbounded, key-value pairs MAY be represented by a generic element with `key`, `value`, and optional `unit` and `scheme` attributes. The `scheme` attribute discriminates between keys from different domains. In that case, also provide a list of keys with human-readable explanations, although it need not be in the same document.

## 9. Binary data

> **Note:** There are no universal rules for deciding whether binary data belongs in an XML document. If it is too large, linking to it is probably better.

1. Binary data MUST NOT be included directly in XML documents. It MUST be encoded using Base64. *Rationale: XML does not allow arbitrary binary bytes.*
2. Base64 line breaks MAY be omitted. *Rationale: Line breaks keep plain-text lines short, but XML is not plain text.*
3. An `xsi:type` attribute with the value `xs:base64Binary` MAY be attached to the element to signal that Base64 is in use. *Rationale: Opaque blobs should include decoding instructions.*

## 10. Processing instructions

1. New processing instructions MUST NOT be created except to specify purely local processing conventions and SHOULD be avoided altogether. Existing standardized processing instructions MAY be used. *Rationale: Processing instructions fit awkwardly into XML data models and can always be replaced by elements; they exist primarily to preserve backward compatibility.*

## 11. Representation of XML document instances

> **Note:** These points are guidelines because the format of program-created instances is often outside the programmer's control, such as when using an XML serialization library. *In no case* should XML parsers rely on these guidelines being followed. Use standard XML parsers, not hand-rolled alternatives.

1. The character encoding SHOULD be UTF-8. Exceptions require extremely compelling circumstances. *Rationale: UTF-8 is universal and widely used.*
2. Namespaces SHOULD be declared in the document's root element wherever possible. *Rationale: Clarity and consistency.*
3. The mapping of namespace URIs to prefixes SHOULD remain constant throughout the document and SHOULD also be used in the design documentation. *Rationale: Clarity and consistency.*
4. Well-known prefixes such as `html:` for XHTML, `dc:` for Dublin Core metadata, and `xs:` for XML Schema SHOULD be used for standard namespaces. *Rationale: Human readability.*
5. Redundant whitespace in a tag SHOULD NOT be used. Use one space before each attribute in a start tag. If the start tag is too long, the space MAY be replaced by a newline. *Rationale: Consistency and conciseness.*
6. Empty elements MAY be expressed as empty-element tags or as a start tag immediately followed by an end tag. Applications MUST NOT distinguish between these forms. *Rationale: XML parsers do not distinguish between them.*
7. Documents MAY be pretty-printed using two-space indentation for child elements. Elements containing character content SHOULD NOT be wrapped. Long start tags MAY be broken across lines, possibly with extra indentation, after any attribute value except the last. *Rationale: General compatibility with this style. Wrapping character content affects its value.*
8. Attribute values MAY be surrounded by quotation marks or apostrophes. Specifications MUST NOT require or forbid either form. `&apos;` and `&quot;` may be used to escape each type of quote. *Rationale: XML parsers do not report the distinction.*
9. Comments MUST NOT carry real data. Comments MAY contain TODOs in hand-written XML. Comments SHOULD NOT be used in publicly transmitted documents. *Rationale: Parsers often discard comments.*
10. If comments are used, they SHOULD appear only in the document prolog or in elements containing child elements. When pretty-printing is required, format comments like elements but wrap their lines. Comments SHOULD NOT appear in elements containing character content. *Rationale: Whitespace in and around comments improves readability, but a comment embedded in character content can cause confusion about which whitespace belongs to the content.*
11. Comments SHOULD have whitespace after `<!--` and before `-->`. *Rationale: Readability.*
12. CDATA sections MAY be used; they are equivalent to using `&amp;` and `&lt;`. Specifications MUST NOT require or forbid CDATA sections. *Rationale: Few XML parsers report the distinction, and combinations of CDATA and text are often reported as single objects.*
13. Entity references other than the standard XML entity references `&amp;`, `&lt;`, `&gt;`, `&quot;`, and `&apos;` MUST NOT be used. Character references MAY be used, but actual characters are preferred unless the character encoding is not UTF-8. Textual formats are exempt from this rule.

## 12. Elements vs. attributes

> **Note:** There are no universal rules for choosing between attributes and elements. Consider the following points; no rationales are provided.

### 12.1. General points

1. Attributes are more restrictive than elements, and every design has some elements. An all-element design is therefore simplest, which does not necessarily make it best.
2. In a tree-style data model, elements are typically represented internally as nodes, which use more memory than the strings used to represent attributes. Nodes may also belong to different application-specific classes, whose representation consumes additional memory in many languages.
3. During streaming, elements are processed one at a time and possibly piece by piece, depending on the XML parser. All attributes of an element and their values are reported at once, which consumes memory, particularly when attribute values are long.
4. Both element content and attribute values require appropriate escaping, so escaping should not influence the design.
5. Some programming languages and libraries make elements easier to process; others make attributes easier. Avoid using ease of processing as a criterion. XSLT, in particular, handles both equally well.
6. If data should usually be shown to the user, consider an element; otherwise, consider an attribute. This rule is often violated for practical reasons.
7. When extending an existing schema, follow analogous patterns in that schema.
8. RELAX NG and Schematron treat elements and attributes symmetrically. Older schema languages, such as DTDs and [W3C XML Schema](https://www.w3.org/TR/2004/REC-xmlschema-0-20041028/ "XML Schema"), tend to provide better support for elements.

### 12.2. Using elements

1. If something might appear more than once in a data model, use an element rather than attributes named `foo1`, `foo2`, `foo3`, and so on.
2. Use an element for information that is an independent object and relates to other information through a parent-child relationship.
3. Use elements when data incorporates strict typing or relationship rules.
4. If order matters between two pieces of data, use elements; attributes are inherently unordered.
5. If data has or might gain its own substructure, use an element; representing substructure in an attribute is always messy. Similarly, if data is a constituent part of a larger piece of data, put it in an element.
6. As an exception to the previous rule, multiple whitespace-separated tokens can safely be placed in an attribute. In principle, the separator can be anything, but schema validators can generally handle only whitespace, so prefer whitespace.
7. If data extends across multiple lines, use an element because XML parsers convert newlines in attribute values to spaces.
8. If data is very large, use an element so that its content can be streamed.
9. If data is in a natural language, use an element so that the `xml:lang` attribute can identify the language. Some natural-language text, such as Japanese, often uses [annotations](https://www.w3.org/TR/2001/REC-ruby-20010531 "Ruby Annotation") conventionally represented by child elements. Right-to-left languages such as Hebrew and Arabic may similarly require child elements to manage [bidirectionality](https://www.w3.org/International/articles/inline-bidi-markup/ "Inline markup and bidirectional text") correctly.

### 12.3. Using attributes

1. If data is a code from an enumeration, code list, or controlled vocabulary, put it in an attribute when possible. Examples include language tags, currency codes, and medical diagnostic codes.
2. If data is metadata about other data, such as a class, a role served by the main data, or a processing method, put it in an attribute when possible.
3. If data is an ID for other data or a reference to an ID, put the identifier in an attribute. For IDs, use the attribute name `xml:id`.
4. Hypertext references are conventionally placed in `href` attributes.
5. If data applies to an element and its descendants unless overridden, conventionally place it in an attribute. Examples include `xml:lang`, `xml:space`, `xml:base`, and namespace declarations.
6. If terseness is the most important concern, use attributes, but consider gzip compression instead; it works well on documents with repetitive structures.

## 13. Parting words

Use common sense and *BE CONSISTENT*. Design for extensibility. You *are* going to need it. *Rationale: Long and painful experience.*

When designing XML formats, take a few minutes to examine other formats and determine their style. Style guidelines let readers concentrate on what you are saying rather than how you are saying it.

Break *ANY OR ALL* of these rules, including those that say MUST, rather than create a crude, arbitrary, or inconsistent design by following them slavishly. Random mixtures of attributes and child elements are difficult to follow and use. However, using both often makes sense when data falls into distinct groups, such as simple and complex data or metadata and primary data.
